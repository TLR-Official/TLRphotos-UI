> ⚠️ 本规则为强制执行项。任何涉及代码变更的操作完成后，必须同步评估并更新版本号。

## 2. 语义化版本规范 (Semantic Versioning)

版本号格式为 `MAJOR.MINOR.PATCH`（主版本.次版本.修订版本），例如 `1.0.0`。

### 2.1 主版本号 (MAJOR) — 不兼容的变更

当发生以下情况时，主版本号 +1，次版本号和修订版本号归零：

- 架构级重构（如从 NocoBase 迁移到纯代码后端）
- API 契约破坏性变更（接口路径、请求/响应结构不兼容旧版）
- 数据库结构不兼容变更（需要数据迁移或清空）
- 核心技术栈更换（如框架、数据库引擎替换）
- 大范围功能删除或合并

**示例**：`1.0.0` → `2.0.0`

### 2.2 次版本号 (MINOR) — 向后兼容的新功能

当发生以下情况时，次版本号 +1，修订版本号归零：

- 新增功能模块（如新增管理后台、图片缓存系统）
- 新增 API 接口（不破坏已有接口）
- 数据库新增字段或表（向后兼容）
- 现有功能的显著增强（如审核流程大改、上传页面改版）
- UI 重大改版（新增页面或大幅调整布局）

**示例**：`1.0.0` → `1.1.0`

### 2.3 修订版本号 (PATCH) — 向后兼容的问题修复

当发生以下情况时，修订版本号 +1：

- Bug 修复（如修复上传失败、修复路由错误）
- 性能优化（如图片代理流式传输）
- 安全漏洞修复（如 JWT 密钥硬编码修复）
- 代码重构（不影响功能和接口）
- 样式微调（不影响布局结构）
- 配置变更（如 Nginx 超时配置）
- 文档更新（如添加注释）

**示例**：`1.0.0` → `1.0.1`

## 3. 版本更新流程

### 3.1 评估时机

**每一次**完成用户明确要求的变更并准备提交时，必须按以下决策树评估版本号是否需要更新：

```
本次变更是否破坏向后兼容（API/数据库/架构）？
├── 是 → MAJOR +1，MINOR 归零，PATCH 归零
└── 否 → 本次变更是否新增功能或显著增强现有功能？
        ├── 是 → MINOR +1，PATCH 归零
        └── 否 → 本次变更是否为修复/优化/文档？
                ├── 是 → PATCH +1
                └── 否（纯讨论/无代码变更）→ 不更新版本号
```

### 3.2 更新位置

版本号更新时，必须同步修改以下位置：

1. **`package.json`** 的 `"version"` 字段
2. **`.ai/context.md`** 的 Changelog 顶部追加版本变更条目

### 3.3 Changelog 记录格式

在 `.ai/context.md` 的 `## Changelog` 章节顶部追加版本变更条目，格式如下：

**主版本/次版本更新**（必须单独一行标注版本号）：

```
| YYYY-MM-DD HH:mm | [release] 版本号升级至 VX.Y.Z — 本版本摘要说明 | 全项目 |
```

**修订版本更新**（可合并到当次变更条目中）：

```
| YYYY-MM-DD HH:mm | [fix] 描述 (VX.Y.Z) | 关联文件 |
```

### 3.4 执行顺序

1. 完成代码变更
2. 评估版本号变更类型
3. 更新 `package.json` 的 `version` 字段
4. 在 `.ai/context.md` Changelog 顶部追加版本变更条目
5. 执行 Git 提交（Commit Message 中包含版本号）
6. 推送到远程仓库

## 4. Git 提交规范补充

涉及版本号变更的提交，Commit Message 格式调整为：

```
[类型] 简要描述 | VX.Y.Z | YYYY-MM-DD HH:mm
```

**示例**：
- `[release] 版本号升级至 V1.1.0 — 新增图片缓存系统 | V1.1.0 | 2026-08-20 15:30`
- `[fix] 修复上传500错误 | V1.0.1 | 2026-08-16 10:00`

## 6. 规则优先级

本规则与《强制性项目规范》具有同等优先级。当涉及版本号管理时，以本规则为准。若用户指令与本规则冲突，必须明确告知冲突点并获得显式确认后方可例外执行，且需在 Changelog 中标注 `[override]`。
