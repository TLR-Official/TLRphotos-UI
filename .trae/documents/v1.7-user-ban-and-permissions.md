# V1.7.0 用户管理功能模块：账号封禁 + 精细化功能权限控制

## 概要

在管理后台用户管理模块新增两项能力：

1. **账号封禁**：管理员可封禁指定用户，触发强制下线；被封禁用户重新登录时收到"该账号已被封禁"提示且无法登录；可解封恢复。
2. **精细化功能权限**：对单个用户单独禁用四项功能 — 发送图片（上传）、查看图片、下载图片、点赞。所有权限变更操作记录审计日志（操作人/时间/被操作用户/变更内容）。

## 用户确认的决策

* **权限生效范围**：仅登录态生效。受限用户登录时被拦截查看/下载；匿名访客仍可公开浏览（保留公开画廊）（但不允许下载）。全账号封禁作为终极手段（无法登录）。

* **封禁与禁用共存**：保留原"启用/禁用"切换按钮，新增独立"封禁/解封"按钮。两者均操作 `is_active`，但封禁用独立字段 `banned_at` 标记语义，登录提示与日志 action 不同。

## 实施变更

### 变更 1：数据库 schema 迁移

**文件**：`backend/src/db.ts`（initDb 函数内，CREATE TABLE users 之后）

为 users 表追加 5 列（用 try-catch ADD COLUMN，兼容旧版 SQLite 无 IF NOT EXISTS，项目既有约定）：

* `banned_at TEXT` — 封禁时间戳，NULL=未封禁；封禁与"软禁用"的语义区分标记

* `can_upload INTEGER DEFAULT 1` — 允许上传

* `can_view INTEGER DEFAULT 1` — 允许查看

* `can_download INTEGER DEFAULT 1` — 允许下载

* `can_like INTEGER DEFAULT 1` — 允许点赞

```typescript

for (const col of [
  'banned_at TEXT',
  'can_upload INTEGER DEFAULT 1',
  'can_view INTEGER DEFAULT 1',
  'can_download INTEGER DEFAULT 1',
  'can_like INTEGER DEFAULT 1',
]) {
  try { await db.run(`ALTER TABLE users ADD COLUMN ${col}`); } catch { /* 列已存在 */ }
}
```

### 变更 2：共享认证 helper（带权限加载与封禁检查）

**文件**：`backend/src/services/authService.ts`

新增 `loadAuthUser(req)` helper：

* 解析 Bearer Token → userId（无效/缺失返回 null，不报错，用于公开路由匿名放行）

* 查询 users 表（含 is\_active, banned\_at, can\_upload, can\_view, can\_download, can\_like）

* 返回 `{ user, error }`：

  * 无 token → `{ user: null, error: null }`（匿名）

  * token 有效但 banned\_at 非空 → `{ user: null, error: { code: 'USER_BANNED', message: '该账号已被封禁', status: 401 } }`（强制下线效果：任何需登录操作都失败）

  * token 有效但 !is\_active 且 banned\_at 空 → `{ user: null, error: { code: 'USER_DISABLED', message: '用户已被禁用', status: 401 } }`

  * 正常 → `{ user, error: null }`

供两类路由调用：

* **强制登录路由**（上传/点赞）：`const { user, error } = loadAuthUser(req); if (error || !user) return res.status(error?.status||401).json(...)`

* **公开路由**（查看/下载）：匿名放行；有 token 且受限才拦截

同步修改 `getUserById` 返回新字段（供 /me 接口使用）。

### 变更 3：登录封禁提示

**文件**：`backend/src/services/authService.ts` — `login()` 函数

将现有的 `if (!user.is_active)` 检查改为先判 banned\_at：

```typescript
if (user.banned_at) {
  throw new Error('该账号已被封禁');
}
if (!user.is_active) {
  throw new Error('用户已被禁用');  // 保留原"软禁用"提示
}
```

登录 SELECT 需追加 `banned_at` 字段。

### 变更 4：管理后台新增 3 个接口

**文件**：`backend/src/routes/admin.ts`（在现有 `/users/:id/toggle` 之后）

均 `adminAuthMiddleware + requireRole(['super'])` + `logAdminAction` 审计：

1. **`POST /users/:id/ban`** — 封禁用户

   * `UPDATE users SET is_active=0, banned_at=?, updated_at=? WHERE id=?`

   * `deleteUserSessions(id)` — 强制下线所有"记住我"会话

   * `logAdminAction(req.admin, 'ban_user', 'user', id, { username, banned_at }, req.ip)`

   * 返回 `{ success: true, message: '用户已封禁' }`

2. **`POST /users/:id/unban`** — 解封用户

   * `UPDATE users SET is_active=1, banned_at=NULL, updated_at=? WHERE id=?`

   * `logAdminAction(req.admin, 'unban_user', 'user', id, { username }, req.ip)`

   * 返回 `{ success: true, message: '用户已解封' }`

3. **`PUT /users/:id/permissions`** — 更新功能权限

   * body: `{ can_upload?, can_view?, can_download?, can_like? }`（0/1，仅传需变更的）

   * 先 SELECT 当前值 → 计算变更项 → UPDATE 仅变更字段 → `logAdminAction(req.admin, 'update_permissions', 'user', id, { changes: { from, to, field } }, req.ip)` 记录每项 from→to

   * 返回更新后权限快照

修改现有 `GET /users/list` 的 SELECT 包含新字段（banned\_at, can\_\*）。

## 假设与约定

* 封禁 = `is_active=0` + `banned_at=时间戳`；解封 = `is_active=1` + `banned_at=NULL`。原 toggle 仅翻转 is\_active 不动 banned\_at（软禁用语义保留）。

* "强制下线"通过 `loadAuthUser` 在每个需登录接口检查 banned\_at/is\_active 实现（现有 JWT 立即失效用于所有需鉴权操作）+ `deleteUserSessions` 清理记住我会话。

* 权限仅登录态生效：匿名访客可公开浏览/下载已审核照片；受限用户登出后可匿名访问（用户已确认接受，全账号封禁为终极手段）。

* `can_view` 拦截点：GET /:id 详情 + GET /image/\* 图片代理（有 token 时）。`can_download` 拦截点：GET /image/\*?download=1（有 token 时）。

* 审计日志 action 命名：`ban_user` / `unban_user` / `update_permissions`，target\_type='user'，details 含变更前后值。

* 版本：MINOR 升级 V1.6.1 → V1.7.0（新增用户权限管理功能模块）。
