# 论坛系统第一阶段：三级嵌套评论 - 产品需求文档

## Overview

- **Summary**: 论坛系统分阶段研发的第一阶段，交付一套**通用三级嵌套评论体系**，同时挂载于照片详情页与专栏文章详情页。评论数据具备完整生命周期管理：新评论驻留服务器本地 SQLite，超期线程自动归档至阿里云 OSS 并从本地清除，客户端经预签名 URL 直读并缓存；基于启发式热度评分与增速预测实现三档动态留存与回迁机制。所有 UI 组件、数据层与状态逻辑均封装为主题参数化的可复用模块，供第二阶段论坛子页面零改动接入。
- **Purpose**: 为照片与文章提供结构化讨论能力并沉淀论坛通用底层；通过 10 天自动归档控制本地数据盘膨胀，同时让热门讨论保持本地访问性能；归档可回迁、不丢数据。
- **Target Users**:
  - 已完成邮箱确权的注册用户：发表主评论、回复、点赞、删除自己的评论。
  - 匿名访客：阅读评论；在发起交互时获得登录/确权引导。
  - 管理员：删除任意评论并留审计记录；对极热评论的长期留存标记进行管理。

## Goals

1. 严格三级嵌套：L1 针对照片/文章的主评论；L2 主评论下的直接回复；L3 回复之间的互相引用回复；深度封顶 3，L3 节点之间继续回复时不再增加缩进层级。
2. 通用可复用：评论能力基于 `(subject_type, subject_id)` 主题模型构建，组件、Hook、API、树算法全部模块封装，后续论坛帖子（`subject_type=thread`）直接复用。
3. 生命周期管理：主评论年龄在保留期内的完整线程（含全部回复）驻留本地；超期线程序列化归档到 OSS，本地删除数据行但保留归档索引；客户端签名 URL 直读 + IndexedDB 缓存。
4. 热度驱动留存：以回复数、评论点赞数为主要信号、结合时间衰减与近期增速线性预测，划分普通/热门/极热三档，支持滚动续期、动态调整与长期留存。
5. 回迁机制：对已归档线程发表回复时，服务端先从 OSS 拉回完整线程再追加回复，线程重新活跃。
6. 旧数据迁移：将现有单层文章评论一次性迁移为新体系下的 L1 评论，内容、作者、时间完整保留。

## Non-Goals

- 论坛子页面、板块、帖子发布与帖子流（第二阶段）。
- @ 提及通知、消息中心、邮件/短信通知（本期"回复@用户"仅做展示文案）。
- 评论编辑功能（仅支持删除）。
- 富媒体评论（图片、表情面板、Markdown 渲染）；本期为纯文本（保留换行），长度受限。
- 真正的机器学习模型或外部预测服务。
- 评论举报与独立审核工作流（管理员删除即本期的管理手段）。
- 评论级别的浏览埋点（热度不依赖独立的评论浏览计数）。

## Background & Context

- 现有评论为单层 `comments` 表（`id, article_id, author, content, created_at`），文章路由提供 `GET/POST /api/articles/:id/comments`，前端 `ArticleDetailPage` 平铺展示；照片无评论能力。
- 可复用基础设施：`ossService`（S3 兼容协议，`uploadBufferToOSS`、预签名 GET 24h，bucket `tlr-main`，香港区域，域名匹配站点 CSP 的 `*.aliyuncs.com`）；`server.ts` 定时任务模式（启动即跑 + 24h 间隔）；`requireVerifiedEmail` 确权门（匿名 401 `AUTH_REQUIRED`、未确权 403 `EMAIL_VERIFICATION_REQUIRED`）；Turnstile 高危验证门；`logAdminAction` 审计。
- 用户决策（2026-10-10）：照片页与文章页**同时迁移**；归档采用**签名 URL 直读 + 回复时回迁**；热度采用**启发式评分 + 增速预测**；删除权限为**本人 + 管理员**。

## Functional Requirements

### 主题与结构

- **FR-1 主题模型**: 每个评论线程绑定 `(subject_type, subject_id)`；一期 `subject_type ∈ {photo, article}`。写入时主题必须存在，否则拒绝。
- **FR-2 节点结构**: 每条评论包含 `root_id`（L1 为自身 id）、`parent_id`（L1 为空）、`depth ∈ {1,2,3}`、`reply_to_user_id` 与 `reply_to_user_name`（L3 互回时指向被回复者，用于展示"回复@用户"）。
- **FR-3 三级封顶规则**:
  - L2 的 parent 必须是同一 root 下的 L1；L3 的 parent 必须是同一 root 下的 L2 或 L3。
  - 当被回复节点 `depth=3` 时，新评论 `depth` 仍为 3（root、主题不变，`reply_to_*` 指向被回复的 L3 作者），前端在 L3 层平铺展示——系统中永不出现 `depth=4`。

### 发表与读取

- **FR-4 发表评论/回复**: 须邮箱确权；参数包含主题、`parent_id`（可空）、内容；服务端计算 depth、root、reply_to；内容必填且 ≤1000 字；同步更新主题评论计数（文章 `articles.comment_count` 口径保持；照片补充同口径计数）。
- **FR-5 线程读取**:
  - 活跃线程（本地）：L1 分页返回（默认每页 20 条，支持按最新/最热排序）；每个 L1 携带其下全部 L2/L3（单楼回复数量设上限，超出时按"查看全部 n 条回复"二次加载，上限默认 100）。
  - 归档线程：本地仅返回归档索引条目；客户端凭归档条目向服务端换取 OSS 预签名 URL 后直读，展示明确的归档加载态。
- **FR-6 评论点赞**: 新增 `comment_likes`，确权用户可点赞/取消，联合主键去重、幂等，评论维护 `like_count`；点赞是热度信号之一。

### 生命周期与存储

- **FR-7 归档作业（每日）**: 扫描超过有效留存期（基础 10 天，可被热度续期覆盖）的 L1 线程：将整线程（含元数据与版本号）序列化为 JSON 上传 OSS（key 前缀 `comments-archive/`）→ 校验对象存在与大小 → 写入归档索引 → 删除本地全部相关数据行。流程幂等、可重入，失败重试且不产生脏数据。
- **FR-8 归档索引**: 记录 root_id、主题、oss_key、归档时间、楼主发布时间、回复数、归档时热度档位、最后回复时间。
- **FR-9 热度算法**:
  - 信号：线程回复总数、全楼获赞总数、时间衰减；以近 48 小时新增回复/点赞计算**增速**，做线性外推得到"预测热度"。
  - 三档：`normal`（保留期 10 天）、`hot`（每日复算时若仍达标则 `retain_until` 滚动 +7 天）、`viral`（长期留存，默认 365 天；`pinned` 标记后不受到期影响，直至管理员取消）。
  - 每次发表回复、点赞时增量重算；阈值与保留天数全部可经环境变量配置。
- **FR-10 回迁**: 对已归档线程发表回复时，服务端凭索引从 OSS 拉取 JSON，做结构与主题校验后将全部评论原样写回本地（保留原始 id、作者与时间戳），再追加新回复并更新计数；索引标记为已回迁（保留回迁记录，OSS 快照保留）。

### 删除与迁移

- **FR-11 删除**:
  - 本人可删除自己发布的评论；删除 L1 即整楼删除（活跃线程删本地数据行；已归档线程同时删除 OSS 对象与索引）。
  - 管理员可删除任意评论（整楼或单条），写入 `admin_logs`；高危删除经 Turnstile。
  - 旧迁移评论（无 user_id）只能由管理员删除。
- **FR-12 历史数据迁移**: 启动迁移将 `comments` 表全部记录转为 `subject_type=article` 的 L1 评论（root_id=新评论 id，depth=1，保留 author 文本，user_id 为空，时间沿用），数量与内容逐条可核对；迁移前做数据库备份；迁移幂等；新老接口完成切换后旧表停止使用。

### 前端可复用模块

- **FR-13**:
  - 组件：`CommentComposer`（主评论输入）、`CommentReplyBox`（回复输入）、`CommentItem`（节点展示）、`CommentThread`（单线程容器，处理折叠/展开）、`CommentList`（L1 分页、排序、加载态、空态、错误重试）、`ArchiveBanner`（归档提示与云读取）。
  - Hook：`useComments(subjectType, subjectId)`（发表/回复/删除/点赞/分页/排序的统一状态入口）、`useArchivedThread`（签名 URL 获取 + IndexedDB 缓存 + 失效重取）。
  - 数据与算法：`src/api/comments.ts` 主题参数化封装；`buildCommentTree`、`flattenTree`、depth 守卫、时间格式化复用。
  - 照片详情页与文章详情页均接入，除主题参数外无场景分叉；视觉遵循白底、teal 强调、无紫色、无 dark 模式。

## Non-Functional Requirements

- **NFR-1 性能**: 本地评论列表接口常规响应 <100ms（主题、root、时间列建索引）；前端 1000 节点建树/平铺 <100ms；归档冷读展示明确加载态，不阻塞页面其余内容。
- **NFR-2 数据完整性**: 归档遵循"先写云并校验、后删本地"；作业单实例锁防重入；任意中断后重启重跑结果一致；回迁与归档不得产生重复行或孤儿行。
- **NFR-3 安全**: 发表/回复/点赞/删除均鉴权；纯文本经 React 自动转义，禁止注入 HTML；回迁 JSON 必须通过结构与主题校验；删除严格所有权校验。
- **NFR-4 可测试性**: 保留天数、热度阈值、当前时间均可通过环境变量或函数注入实现确定性测试；归档/回迁在测试环境不依赖真实 OSS（接口可注入）。
- **NFR-5 零新增运维**: 不引入新容器、缓存服务、队列或第三方依赖；OSS 使用现有 bucket 与凭证；每日作业复用现有进程定时机制。

## Constraints

- **Technical**: Node.js + Express + `sqlite`/`sqlite3`（沿用 db.ts 异步封装风格）；React 19 + TypeScript + Tailwind 4；后端监听 127.0.0.1，nginx 反代；CSP 与 nginx 配置不变更（OSS 域名已被现有 CSP 覆盖）。
- **Business**: 低成本、零新增运维；规则对非技术站长可解释；归档数据始终可回迁、可追溯。
- **Dependencies**: 现有 OSS 凭证与 bucket；Turnstile（删除验证门）；现有用户与审计体系。

## Assumptions

- L3 互回采用"平铺 + 回复@用户"的主流展示形态，不产生第 4 层视觉缩进。
- 保留期锚点为 L1 的 `created_at`；续期只修改 `retain_until`，不改历史时间。
- 归档粒度为每个 L1 线程一个 JSON 对象，对象内含格式版本号。
- 热度信号以回复数、点赞数为主，不做评论级独立浏览埋点；权重与阈值经环境变量可调。
- 旧文章评论迁移后无绑定用户，作者名以文本展示，仅管理员可删除。
- OSS 归档对象不配置自动过期（体积小、成本可忽略），删除线程时随对象显式删除。

## Acceptance Criteria

### AC-1: 三级深度封顶
- **Type**: `rule`
- **Given**: 同主题下已有 L1→L2→L3 链条
- **When**: 用户对该 L3 节点再次回复
- **Then**: 新评论 depth=3、root_id 与主题不变、reply_to 指向被回复 L3 的作者；全表查询不存在 depth>3 的记录
- **Pass Condition**: 集成测试连续构造 5 次"再回复"，所有节点 depth≤3 且 parent 链正确
- **Evidence**: 后端集成测试 + SQLite 查询结果

### AC-2: 发表鉴权与校验
- **Type**: `rule`
- **Given**: 任意可评论主题
- **When**: 分别以匿名、未确权用户、确权用户发起发表/回复，以及空内容/超 1000 字/不存在主题/跨线程 parent
- **Then**: 匿名 401 `AUTH_REQUIRED`、未确权 403 `EMAIL_VERIFICATION_REQUIRED`、非法参数 400/404、合法请求 2xx 且计数同步
- **Pass Condition**: 各类状态码与错误码在集成测试中逐一断言通过
- **Evidence**: 评论集成测试报告

### AC-3: 嵌套渲染与交互
- **Type**: `rule`
- **Given**: 一个含 L1/L2/L3 的线程
- **When**: 在照片详情页与文章详情页查看并操作
- **Then**: L1/L2 按层级缩进，L3 平铺并显示"回复@用户"；回复框预填回复目标；折叠/展开、排序、分页正常
- **Pass Condition**: 两个页面浏览器实测全部交互通过
- **Evidence**: 浏览器实测截图/记录与组件测试

### AC-4: 归档作业正确执行
- **Type**: `rule`
- **Given**: 注入保留天数使某线程超期（非热门档）
- **When**: 执行每日归档作业
- **Then**: OSS 对象内容与线程数据一致、归档索引写入、本地相关行删除、主题评论计数口径一致；重复执行不产生副作用
- **Pass Condition**: 隔离库 + OSS 注入实现的集成测试断言全部通过
- **Evidence**: 生命周期集成测试

### AC-5: 归档线程签名直读与客户端缓存
- **Type**: `rule`
- **Given**: 一个已归档线程
- **When**: 客户端请求读取
- **Then**: 先获得归档索引与 OSS 预签名 URL，直读成功并写入 IndexedDB；二次读取优先本地缓存；URL 过期后可重新换取并读取
- **Pass Condition**: 缓存命中、云读取、过期重取三条路径测试通过
- **Evidence**: 前端模块测试与浏览器实测

### AC-6: 归档线程回复回迁
- **Type**: `rule`
- **Given**: 已归档线程
- **When**: 确权用户对其发表回复
- **Then**: 原全部评论原样回到本地（id/时间戳保留），新回复追加成功，计数正确，索引标记已回迁
- **Pass Condition**: 回迁集成测试通过且行数、时间戳逐条核对一致
- **Evidence**: 生命周期集成测试

### AC-7: 热度三档与动态续期
- **Type**: `rule`
- **Given**: 三组确定性信号数据（普通、增速达热门阈值、达极热阈值）
- **When**: 触发热度重算与每日作业
- **Then**: tier 分别为 normal/hot/viral；hot 的 retain_until 滚动 +7 天；viral 长期留存；pinned 不受到期影响
- **Pass Condition**: 确定性输入下档位与时间计算断言全部通过
- **Evidence**: 热度算法单元测试

### AC-8: 删除权限与整楼处理
- **Type**: `rule`
- **Given**: 活跃线程与已归档线程
- **When**: 作者本人、其他用户、管理员分别执行删除
- **Then**: 非作者被拒；本人删 L2/L3 仅删该条；删 L1 整楼清除（归档线程同时删 OSS 对象与索引）；管理员删除写 admin_logs 并经 Turnstile
- **Pass Condition**: 各类删除路径断言通过，审计日志可查
- **Evidence**: 集成测试 + 审计记录核对

### AC-9: 旧文章评论迁移
- **Type**: `rule`
- **Given**: 含 N 条旧 comments 的数据库
- **When**: 启动迁移
- **Then**: 生成 N 条 article 型 L1 评论，作者、内容、时间逐条一致；迁移前生成备份；再次启动不重复迁移；计数一致
- **Pass Condition**: 迁移测试断言数量与字段一致且幂等
- **Evidence**: 迁移测试与备份文件

### AC-10: 评论点赞
- **Type**: `rule`
- **Given**: 确权用户与任意评论
- **When**: 点赞、重复点赞、取消点赞
- **Then**: 计数正确、重复幂等、取消扣减不为负
- **Pass Condition**: 点赞集成测试通过
- **Evidence**: 集成测试

### AC-11: 模块可复用性
- **Type**: `rubric`
- **Dimension**: 评论模块脱离具体场景的可复用程度（主题参数化、无页面硬编码、类型与接口自包含、论坛第二阶段接入成本）
- **Scale**: 1-5
- **Anchors**: 1 = 评论逻辑与页面强耦合，换场景需重写；3 = 组件可复用但状态/数据层仍有场景分叉；5 = 组件/Hook/API/树算法全部主题参数化，新场景仅传 subject 参数即可接入
- **Pass Threshold**: >= 4
- **Evidence**: 模块结构审查 + 两页面接入方式对比 + 独立评审

### AC-12: 存储策略健壮性
- **Type**: `rubric`
- **Dimension**: 归档/回迁/续期在中断、重跑、并发、异常输入下的数据安全与可观测性
- **Scale**: 1-5
- **Anchors**: 1 = 失败会丢数据或产生脏数据；3 = 主流程正确但异常路径覆盖不足、日志难追踪；5 = 全链路幂等、先云后本地、异常可恢复、日志清晰可审计
- **Pass Threshold**: >= 4
- **Evidence**: 故障注入测试 + 日志检查 + 独立评审

### AC-13: 评论交互体验
- **Type**: `rubric`
- **Dimension**: 层级可读性、回复目标清晰度、归档加载态、错误提示、移动端适配
- **Scale**: 1-5
- **Anchors**: 1 = 层级混乱、容易回错对象；3 = 功能完整但层级/提示平庸；5 = 三级结构一眼可读、回复目标明确、归档读取无感过渡、移动端无横向溢出
- **Pass Threshold**: >= 4
- **Evidence**: 两页面桌面端/移动端浏览器实测 + 独立评审

### AC-14: 契约与配置文档同步
- **Type**: `rule`
- **Given**: 一期全部接口与配置项
- **When**: 交付时
- **Then**: `backend/docs/api.md` 完整记录新接口、错误码与归档读取流程；`.env.example` 列出全部新增配置（保留天数、热度阈值等）
- **Pass Condition**: 文档与实际路由逐项核对一致
- **Evidence**: 文档 diff 与路由清单核对
