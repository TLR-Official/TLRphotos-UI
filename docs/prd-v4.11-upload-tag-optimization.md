## 一、项目概述

### 1.1 背景

现有上传流程基于「分区 + 机型」两段式选择，存在信息重复录入；标签体系虽已于 V4.2 落地三层结构，但标签清单缺乏正式定稿；作品集展示以「精选作品」单栏呈现，未按板块组织；详情页权限、审核端删除与清理策略、热门时效均无明确规则。

站长以 5 页手稿集中提出上述问题与改进要求，本 PRD 将其整理为可评审、可执行的需求基线。

### 1.2 目标

1. **修正 4 项线上缺陷**（注册号错位、审核端拖拽失效、作品集乱序、注册号自动查询）；
2. **重构上传表单**，消除信息重复，移动端适配大按钮；
3. **定稿三大板块标签清单**，作为上传页与筛选页的唯一事实来源；
4. **主页板块化**，以 16:9 图片 + 3×3 标签网格替代「精选作品」单栏；
5. **补齐规则类能力**：热门时效、图片压缩规则、上传成功页、详情页权限、清理策略、合作伙伴、传图规则页。

### 1.3 范围

| 范围 | 说明 |
|------|------|
| 包含 | 上传表单重构、标签清单定稿、主页板块化、热门时效、压缩规则、详情页权限、清理作业、合作伙伴区块、传图规则页、4 项 Bug 修复 |
| 不包含 | 机场地图可视化（手稿明确「地图先不做了」）、新闻富文本编辑器改造 |
| 已裁决 | 4.5 传图速度优化采用方案 A：OSS 预签名直传 + 服务端异步生成水印/压缩 |

## 三、上传表单重构（大改）

### 3.1 现状问题

```
目前（以航空为例）：
[航空] → [飞机型号]  ← 信息填写
                 ↑ 双重信息
```

用户先选分区、再选机型，而分区（航空）与机型（窄体机等）语义重叠，导致**同一信息填写两次**，且移动端小屏下表单冗长。

### 3.2 目标结构

**分区驱动动态表单**：先选分区 → 展开该分区专属字段 → 标签多选。

```
[ 分区选择：航空 | 铁路 | 汽车 ]
        ↓ 点击后展开
[ 该分区必填字段表单 ] + [ 标签多选 ]
```

### 3.3 航空表单字段

| 字段 | 必填 | 允许值 | 说明 |
|------|------|--------|------|
| 注册号 | ★ | 2–20 位 `A-Z0-9-` 或 `N/A` | 沿用现有校验；**注册号填一次即可，不再重复出现在机型栏** |
| 拍摄时间 | ★ | 日期时间 | |
| 机型 | ★ | 文本或 `N/A` | |
| 拍摄地点 | ★ | 文本或 `N/A`；支持机场识别补全 | 见 3.6 |
| 标签 | ★（至少 1 个） | 见第五节航空清单 | 多选 |

**标签选择控件（航空示例）**：宽体机、窄体机、货机、直升机、展机（航展）、支线客机、滑翔机、公务机、轻型飞机、大型无人机、彩绘、事故……

**交互要求**：
- 桌面端：复选框；
- **移动端：改为大尺寸按钮（≥44px 高）**，横向可换行排布；
- 「点出 → [xxx]」：标签较多时收起为「更多」展开，见 5.1 排序。

### 3.4 铁路表单字段

| 字段 | 必填 |
|------|------|
| 车号 | ★ |
| 时间 | ★ |
| 车型 | ★ |
| 拍摄线路 | ★ |
| 所属局段 | ★ |
| 标签 | ★（≥1） |

> 手稿红笔注：「不写了，和上边一样，见标签」→ 铁路标签清单见第五节。

### 3.5 汽车表单字段

沿用航空/铁路结构：车辆信息（编号）、拍摄时间、车型、拍摄地点、标签。字段命名以「车辆」为前缀（配合 B1 修复）。

### 3.6 机场识别（航空专属增强）

```
输入：SZX
输出：SZX / ZGSZ  深圳宝安国际机场   [✓ 确认]
```

- 输入 IATA（3 位）或 ICAO（4 位）代码，返回机场全称；
- 确认后写入「拍摄地点」字段；
- 数据源：**开源机场数据库离线内置**（OurAirports / OpenFlights，MIT/PD 授权），前端本地匹配，**不新增后端接口**；
- 手稿明确「地图先不做了」，本迭代不做地图选点。

### 3.7 输入引导

- 输入框内浅灰示例：`dsc 5501 xxxx`；
- 红字标注「仅为格式示例，请谨慎填写」；必填项以 `★` 标识。

## 四、上传后流程与热门时效

### 4.1 上传成功页（不跳详情页）

```
┌──────────────────┐
│   上传成功！  ✓   │
├──────────────────┤
│   返回首页        │
│   返回继续        │
│   继续上传        │
└──────────────────┘
```

- 硬性要求：**提交成功后不自动跳转照片详情页**；
- 三个出口按钮（文案待确认），主按钮为深蓝实底。

### 4.2 热门图片时效

- 审核界面「热门」勾选旁增加**确认动作**：确认通过 = 正式评为热门；对**无热门意愿**的作品不显示该确认；
- 热度时长可选：**10 / 15 / 30 / 60 / 120 / 360 天**；
- 到期自动取消热门标识（定时任务）；
- 存量已评热门数据**不做回溯修改**（手稿：「已处理不用改」）。

**数据影响**：`photos.hot_expires_at`（时间戳，可空）+ 每日到期扫描作业。

### 4.3 详情页图片压缩规则

按原图体积分档决定详情页加载尺寸，**以手稿红笔为准**：

| 原图体积 | 加载比例 |
|----------|----------|
| 0 – 500 KB | 100% |
| 500 KB – 1 MB | 80% |
| 1 MB – 5 MB | 60% |
| 5 MB – 10 MB | 50% |
| 10 MB – 50 MB | 40% |

- 目的：降低移动端流量与解码内存；
- 与现有缩略图/预览图体系的关系：本规则作用于**详情页大图**，列表仍走缩略图。

### 4.4 昵称修改限制

- 昵称**每年最多修改 3 次**；
- 高权限账号可**随时强制修改**任意用户昵称；
- 目的：防止用户通过频繁改名规避追责（手稿反面举例：战雷）；
- 建议同时提供「昵称锁定」开关（高权限可置）。

**数据影响**：`users.nickname_changed_at` 或独立计数表 `nickname_changes`。

### 4.5 传图速度优化（✅ 已裁决：方案 A）

**手稿原始诉求**：图片直接传到服务器，水印生成与压缩由服务器端完成，缩短用户端等待时间。

**裁决结论**（2026-11-14 站长确认）：采用**方案 A**——保留阿里云 OSS 预签名直传，原图不落服务器磁盘；水印与压缩改由服务端在**上传完成后异步**处理，结果回写 OSS。

**决策依据**：

- 方案 B/C 均需要放宽或违反「禁止原图本地存储」硬约束，且引入磁盘清理风险；
- 方案 A 将用户等待压缩为「预签名直传 OSS」单一环节，水印/压缩在后台完成，同样达成手稿的「缩短等待」目标；
- 不新增网络架构与存储介质，符合「极致轻量、零运维」的项目定位。

#### 4.5.1 处理链路

1. 客户端向服务端申请预签名 URL，**直传 OSS 原图**（路径与命名沿用现状）；
2. 上传完成回调（`complete`）返回成功后，服务端登记一条**异步处理任务**；
3. 后台 Worker 从 OSS 拉取原图，按 **4.3 压缩规则**生成详情页大图，叠加 `TLRphotos` 水印，输出 WebP；
4. 派生图回传 OSS 独立对象键，数据库记录派生图路径、尺寸、处理耗时与状态；
5. 详情页/作品集对外展示派生图，原图保留用于审核与归档。

#### 4.5.2 任务状态与失败回退

| 状态 | 含义 | 前端/审核端表现 |
|------|------|------------------|
| `pending` | 已登记，待处理 | 详情页暂用原图展示，标注「处理中」 |
| `processing` | Worker 处理中 | 同上 |
| `done` | 派生图已回写 | 展示带水印压缩图 |
| `failed` | 重试耗尽 | 回退展示原图，记录告警，不影响作品正常浏览 |

- 失败重试 **3 次**（指数退避），仍失败则停留 `failed`，由运维侧可重跑；
- 用户端**不阻塞**：任务提交后立即进入 4.1 上传成功页，不等待处理完成。

#### 4.5.3 实现约束（红线）

- 🚫 **禁止引入 Redis / 独立消息队列**：异步队列以 SQLite 任务表 + 进程内 Worker 轮询实现；
- 🚫 **原图不得持久落盘**：处理过程采用流式读写或系统临时目录，任务结束（含异常）必须删除临时文件，不得写入 `backend/data/` 或数据盘持久目录；
- ✅ 处理逻辑只依赖现有 OSS SDK 与图像处理库，不新增常驻服务；
- ✅ 审核端在 `pending` / `processing` 状态下允许正常审核，审核结论不等待派生图完成。

#### 4.5.4 遗留子项

- 水印是否也需叠加到 OSS 原图本身（当前默认为**仅派生图带水印**，原图保持原件）；若要求原图同步带水印，需评估归档与溯源影响（见 Q16）。

## 七、详情页权限与内容清理

### 7.1 详情页访问收紧

| 角色 | 已过审 | 审核中 | 未通过 |
|------|--------|--------|--------|
| 访客 / 普通用户 | 可打开 | **打不开**，仅见状态栏小图 | **打不开**，仅见状态栏小图 |
| 作品所有者 | 可打开 | 待确认（见 10.4） | 待确认 |
| 管理员 / 审核员 | 可打开 | 可打开（审核必需） | 可打开（审核必需） |

> 手稿原文：「仅过审图片才可打开详情页，审核中和未过审打不开，仅能看状态栏那个小图」。
> 需明确「所有者可查看自己未过审作品」这一现有能力是否延续。

### 7.2 审核端删除权限

- 审核端**可删除图片**；
- **未过审的不可删**（保留证据用于申诉）；
- **已过审的可删**。

### 7.3 自动清理策略

| 规则 | 内容 |
|------|------|
| 清理周期 | 未审满 **1 个月**的图片清理一次 |
| 清理范围 | 原图 + 小预览图一并清除 |
| 申诉时限 | 上传满 **1 周**后禁止申诉 |

### 7.4 清理交互

手稿草图为卡片列表形态：

```
┌──────────────────────┐
│  + 待审              │
├──────────────────────┤
│  作品 A        [删除] │ ← 点这个
│  作品 B        [删除] │
└──────────────────────┘
```

- 列表顶部为「+ 待审」筛选入口；
- 每项右侧「删除」按钮；
- 删除需二次确认（沿用现有三重确认规范中的第二级）。
